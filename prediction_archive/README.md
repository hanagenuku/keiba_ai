# prediction_archive — 公開時点の予想を固定保存する場所

```
prediction_archive/YYYY-MM-DD/{race_id}.json
```

🔴 **ここのファイルは公開後に書き換えない。** これが商品の最大の信用材料
（Phase 4 §18・§19）。`src/product/archive.py` が上書きを拒否する
（`AlreadyPublished`）。テストで固定してある。

## なぜ `data/latest.json` では足りないのか

`latest.json` は**当日の refresh で上書きされる**。2026-09-19〜22 に実害が出ている
（遅延発火した refresh が翌日予想を巻き戻した）。したがって
「公開後に予想を変更していない」ことを読者に示すには、公開時点のファイルが
**別に永続する**必要がある。

## 何が入っているか

公開時刻・AI順位（AI+市場 / AI単独 / 適性）・市場人気・オッズ・印・見解・買い目・
推奨配分・レース信頼度・**入力の指紋（SHA-256）**。結果は `result` キーに**後から追記**する
（予想部分は1つも変更しない。`attach_result()` が検算して変わっていたら落ちる）。

## 結果（`result`）の中身と、入れないもの

`scripts/attach_product_results.py` が結果取得後に追記する（土日のワークフローから
非ブロッキングで動く）。入るのは**事実だけ**:

- `top3` / `placings`（着順。`history.db` の `horse_history.place`）
- `marks` / `danger_favorites`（◎○▲ と「危険視した人気馬」が何着だったか）
- `bets`: 券種・組番・`hit`・`payout_per_100`（100円あたりの払戻）
- `cross_check`: 着順と払戻を**別経路で突合**した結果（`ok` / `mismatch`）

🔴 **回収率は入れない。** 記事は金額を「換算例（推奨額ではありません）」としか
書いていない（§10 資金配分は各自調整）ので、回収率を出すには賭け金の仮定が要る。
仮定を混ぜた数字を「結果」として永久保存すると、後から前提を変えられない。
集計はアーカイブを読む側でやる。

🔴 **的中と払戻は `keiba.db` の `race_dividends` を正とする。着順から自分で判定しない。**
2026-09-27 中山9R は7頭立てで複勝が2着までしか発売されておらず、3着（馬番2）に
複勝配当が無い。一方ワイドは同じレースで3着内の2頭組が成立している。この非対称を
手書きの規則で再現しようとすると必ず誤判定する（テストで固定してある）。

🔴 **結果がまだ取れていないレースには何も書かない。** 空の結果で埋めると全部が
外れとして記録される。次回の実行で改めて拾われる。

## 外れた予想も消さない

§19 のとおり。的中だけを並べると景品表示法の優良誤認のリスクがあり、
そもそも「事前に公開していた」という事実自体が信用の源なので、
消すと商品価値そのものが消える。

## git 履歴も証拠になる

このディレクトリはリポジトリに含める（`.gitignore` しない）。
ファイルの内容とコミット時刻の両方が残るので、
「後から書き換えていない」ことを第三者が確認できる。
