# 2026-11-13②: kayochin 能力指数を採用し、本番モデルを指数つき（136列）に差し替えた

## ユーザーの決定

「kayochin 指数の (a) 採用」。確認測定（`websig/RESULTS_CONFIRM_kayochin.md`）で効果の基準はすべて通り、
対照群A の合格線だけ不合格（カードの線の置き方の誤り・ずれは採用に不利な側）。それを認めたうえでの採用。

## やったこと

### 1. 採用の配管を「本番の形」で通したら、指数が本番に届かない食い違いが4件あった（PR #348 ほか）

| | 学習 | 本番の推論 | そのまま採用していたら |
|---|---|---|---|
| 馬番のキー | `horse_num` | `num` / `post_position` | 指数が1頭にも付かない。既存の `f_post` も全馬「馬番1」扱いだった |
| レースIDのキー | `race_id` | `id` | 指数が1レースにも貼られない |
| 日付の形 | `YYYY-MM-DD`（sitemap） | `YYYYMMDD`（weekend.py） | 当日の記事が1本も一致せず、指数を取りに行かない |
| 性別 | history.db の実値 | parser が捨てていた | （指数とは無関係）`f_sex` が全馬「牡」だった |

- 🔴 **3件は「採用しても本番では効果ゼロ」になる食い違い**。確認測定の +0.0026 は学習側の形でしか出ていなかった。
  2026-09-25 の「一時採用して端から端まで通した」は学習側の形の入力で通しており、本番の形では通していなかった。
- 既存の `f_post`・`f_sex` の食い違いを直す影響は、直近3窓・3シードで **−0.0001 AUC 程度**（◎複勝的中率 62.07 → 62.03%・誤差の範囲）。
- 再発防止: `web_signals.horse_number()` / `race_key()` に一本化し、`tests/test_inference_key_parity.py` が
  **parser の出力そのまま**の形で検査する。

### 2. web 由来の列は NaN のまま通す

学習・推論・較正の `fillna(5.0)` を `web_signals.fill_missing()` に置き換えた。指数の2列だけ NaN を残す
（5.0 で埋めると「順位5位・z=5」という実在の値と区別できない値になる）。較正器の作成（`calibrate_xgb`）でも指数を貼る。

### 3. モデル一式の作り直し（`adopt-web-source.yml`・run 43358018609）

指数DBは非公開 artifact にしか無いので GitHub のランナーで作り、結果をブランチに置いて PR にした。

- 学習の窓は旧モデルと同じ（train_end 2026-06-30・学習 155,187行）。**変えたのは指数の2列を足したことだけ**
- 検証データ（2026-07-01〜08-31・8,215頭）: 新 AUC **0.7880** / 旧 0.7858（Brier 0.1846 / 0.1858）
- 136列・木61本・best_iteration 10。指数2列の重要度は 8.29% と 4.27%
- 指数が付いた学習行: 2023年 79.4% / 2024年 72.3% / 2025年 75.3% / 2026年 76.6%
- 較正器（`xgb_calibrator.pkl`）テスト期間 ECE 0.0147・ability 較正器も作り直した
- ☆モデルは作り直していない（指数を使わない。事前登録した ☆ を動かさないため）

  ⚠ 指数が取れたレースでは2番手以下の並びがこれより動く
