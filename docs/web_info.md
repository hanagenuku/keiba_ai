# 週末の web 情報を予想に取り込む仕組み（2026-09-15）

ユーザー依頼:
> 土曜日曜レースの予想を生成する際、あなたがweb上で有意義な情報を集めて予想に
> 反映する仕組みも作って。予想ツールが予想したものにプラスアルファするのか、
> あなたがwebから得た情報を先に予想ツールに渡してから本番予想を立てるのかは
> どちらがいいのかわからないので、あなたに任せます。

## 結論: **上流（特徴量として先に渡す）。後付けの補正はしない**

理由は好みではなく実績。このプロジェクトで**予想の出力を後から書き換える層は
例外なく撤回されている**:

| 層 | 導入 | 結末 |
|---|---|---|
| 市場補正レイヤー | 2026-06-27 | AIが市場のコピーになり完全廃止（07-14） |
| `error_tags` 週次補正 | 2026-07-14 | 1年近く誰も検証しないまま本番を書き換えていた。検証したら効果ゼロで既定OFF（09-01） |
| `rank_matrix_filter` | 2026-07-27 | 翌日の大規模検証で否定、既定OFF（07-28） |
| 「AI xx%」バッジ | — | 手書きの式で**符号が逆**だった（08-18） |
| 「ROI予測 ~150%」 | — | べた書きの定数だった（08-07） |

後付け層は**モデルと切り離されているので A/B が組めない**。上流に置けば
①学習と推論で同じ列を読む ②重要度も ablation も測れる ③壊れたらテストで落ちる。

## ただし上流に置けるものは限られる

North Star #3「データなしの特徴量追加をしない」。web から取った値を特徴量に
するには、**過去のレースぶんの同じ値**が要る。それが無い情報は学習できない。

いま条件を満たすのは **当日の馬場状態ひとつだけ**。理由は
「新しい列を作る」のではなく「**すでにある列の穴を埋める**」から:

```
f_track_cond   学習時  race_history.track_condition が入る（実データ 94.6% 充足）
               推論時  出馬表に載らないので **つねに 0.0（良）**  ← パリティ違反
良でないレースは実データの 27.2%（稍重16.3 / 重7.8 / 不良3.2）
```

## 2層に分けた

### 層1（自動・モデルに届く）: 当日の馬場状態

`src/scraper/going.py`。**その日すでに終わったレースの結果**から馬場状態を読み、
まだ発走していない同じ会場×馬場のレースに反映する。

- 🔑 web の要約ではなく**JRA の結果ページの実データ**。日付を取り違えようがない
- 🔑 リークではない。予測対象より**前**に終わったレースの公開情報だけを使う
  （2026-08-06 の当日馬場バイアスと同じ線引き）
- ⚠ 8時台のrunでは1レースも終わっていないので**実行しない**。11:30 / 14:00 のrunで動く
- ⚠ North Star #4 に従い二重の上限（会場あたり12リクエスト / 全体480秒）。
  超えたら黙って諦め、**予想は止めない**（2026-07-18 のタイムアウト事故）
- ⚠ 環境変数 `COLLECT_GOING=0` で無効化できる

**効果は小さいと事前に分かっている。** 2026-08-26 に本番 `calc_all` を4通り回した
実測では、馬場を変えて軸が入れ替わるのは **2.5%** のレースだけ、勝率の変化は
中央値 0.03pt。ここで直すのは「当たるようになるから」ではなく
**学習と推論で違う値を渡している状態を解消するため**。
副次的に、展開予想モデルから外した `cond`（馬場）を戻せる道が開く。

### 層2（Claude・記録のみ）: 週末の情報収集

土日の朝に Routine が新しいセッションを立ち上げ、web で集めた情報を
`data/web_notes/YYYY-MM-DD.json` に記録する。スキーマは `data/web_note_schema.json`。

🔴 **予想には一切反映しない。** 理由:

1. この環境は **egress proxy で個別ページに到達できない**（`jra.go.jp`・
   `radionikkei.jp` とも EGRESS_BLOCKED を実測）。使えるのは WebSearch の**要約**だけで、
   要約は**複数の日付が混ざる**（実測で確認済み）。そのまま特徴量にすると
   「間違った馬場を静かに配る」ことになる
2. 過去分の web 情報が無いので学習データが作れない（North Star #3）
3. 上の表のとおり、検証を通していない層は本プロジェクトでは必ず撤回されている

**順序**: ①記録だけ回す ②溜まる ③**基準を先に書く** ④測る ⑤通れば繋ぐ。
パドック入力（2026-09-02）と完全に同じ扱い。

## 集める対象（層2）

| 種類 | 何に使えるか | いまの扱い |
|---|---|---|
| 馬場状態・使用コース（A/B/C） | `f_track_cond` の裏取り・R1〜R3 の穴埋め候補 | 記録のみ |
| 当日の天候・降水 | 馬場の先読み | 記録のみ |
| 出走取消・騎手変更 | 出馬表の再取得で既に拾えている可能性が高い。差分の検知用 | 記録のみ |
| 馬場の傷みの位置（内が荒れている等） | 2026-08-06 に当日馬場バイアスを実測して **-0.0005**。期待はしない | 記録のみ |

⚠ 調教タイム・厩舎コメントは**打ち切り済み**。JRA公式に機械可読のタイムは存在せず
（2026-08-16 に実HTMLで4回検証）、netkeiba は有料（2026-08-25）。web検索の要約で
代替できる情報ではないので、層2でも追わない。

## 効果をどう判定するか（層2を繋ぐときの手順）

1. `data/web_notes/` が 20開催日ぶん溜まる（約2.5ヶ月）
2. `confidence == 'official'` の行だけを対象にする
3. 事前に基準を書く。最低でも: 対照群・前後半・3本抜き・N・複数窓
4. 本番同型 A/B（134特徴量 vs +web列）を3窓×3シードで回す
5. 通らなければ繋がない。**「様子を見る」で本番に入れない**
