## 🌟 North Star（絶対に守るルール・最初にこれだけ読む）

このセクションはこのファイルが肥大化しても劣化させないための最重要ルールの抜粋。
詳細な経緯は各ルール末尾の日付から本文の該当セッションを参照。

1. **市場オッズ（win_odds等）を特徴量に追加しない**（DESIGN.md「6. やってはいけないこと」）。
   精度は上がって見えても市場コピー化してエッジが消える（2026-07-06〜09で実際に発生・後述）
2. **コード変更は作業ブランチ→PR→CI確認→mainマージ**。main直pushはしない
   （GitHub Actionsが自動生成するdata/配下のコミットのみ例外）。
   ⚠ **破りやすいのは「PRをマージした直後」**。2026-09-22 に実際に踏んだ——
   マージ後に `git checkout main && git pull` でローカルを同期し、**そのまま次の作業を
   コミットして push** してしまった（ドキュメント1ファイルで実害は無かったが規約違反）。
   🔑 **マージしたら、次の作業を始める前に作業ブランチへ戻す**。
   マージ済みPRのブランチは `git fetch origin main && git checkout -B <branch> origin/main`
   で作り直してよい（マージ済み履歴しか無いことを両方向の diff で確かめてから force-with-lease）
3. **データなしの特徴量追加をしない**。追加する場合は学習時と推論時で同じ経路・同じ値が
   入ることを確認する（学習/推論パリティ）。パリティが崩れると片方だけ静かにデフォルト値化する
4. **スクレイピングに新規リクエスト元を追加する際は、件数上限(budget)を必ず設ける**。
   無制限だと導入直後に全件が"新規"扱いになりCIタイムアウトでその回のデータが丸ごと失われる
   （2026-07-18で実際に発生）
5. **実験用の一時ファイル・ノートブックを本番コードパス（data/直下・リポジトリ直下）に
   コミットしたままにしない**。「存在すれば優先ロード」する設計だと消し忘れが本番モデルを
   サイレントに無効化する（2026-07-16で実際に発生）
6. **テストは「本番と同じデータ型・同じフォーマット」で書く**。DBの行を扱うコードは
   手打ちdictではなく実際に`sqlite3.Row`として取り出したもので、スクレイパーは
   綺麗な自作HTML文字列ではなく実機のHTML構造を模したfixtureで、モデルファイルを
   読むコードは実際にpickle/xgboost UBJ等その形式で保存したファイルで検証する。
   「本物に似ているが微妙に違う代用品」でテストするとテストは通り続けるが本番だけ壊れる、
   という事故がこの1ヶ月で複数回発生した（`sqlite3.Row.get()`未対応・Shift_JIS未指定・
   GitHub/Drive間history.dbスキーマずれ等、いずれもテストは通っていたのに本番で発覚。
   2026-07-22③〜07-23④で繰り返し確認・2026-07-23⑥セッションでNorth Star格上げ）
7. **小さいNの好成績を信じない。買い目・戦略の採用前に必ず大規模out-of-sample検証を通す**。
   2026-07-27に導入した買い目フィルタは本番76点・4開催日でROI 182.8%だったが、
   翌日の約2,000レース検証で**71.3%**と判明し撤回した（2026-07-28）。
   検証手段は `KEIBA_買い目フィルタ検証_v1.ipynb`（過去データで再学習し
   look-ahead biasを避ける設計）。**「数週間フォワードで様子を見る」より
   過去データで即座に大規模検証する方が速く確実**
8. **異常に良い数字を見たら、喜ぶ前にまず特徴量のリークを疑う**。
   2026-07-30に「回収率261%のセグメントを発見」したが、正体は`member_level`が
   相手馬の**そのレース以降の成績**を使っていたリークだった（完全撤回）。
   同時に`first_3f`（そのレース自身の前半3F）・`running_style`（学習時のみ確定値）も
   発見され、**過去のオフライン評価は本番性能を約0.035 AUCぶん過大に見せていた**。
   ルール7（小さいNを信じない）とは別物で、**Nが大きくてもリークがあれば数字は嘘になる**。
   チェック方法は「その値はレース**開始前**に本当に手に入るか」を1特徴量ずつ問うこと。
   ⚠ **リークは値そのものより「値の作り方」に潜む**（2026-08-08に再発）。
   Plackett-Luceレーティングで「AUC +0.037 / 回収率115%」と誤報告したが、正体は
   **θが同値の馬のタイブレークが着順順に並んでいた**こと（SQLが `ORDER BY place`）。
   θ自体は完全に正しく、θを対象にした検査（初出走馬が厳密に0・同日内で不変・
   着順との相関）は**全部通っていた**。
   🔑 **プラセボ対照（レース内で値をシャッフル）はリーク検出に使えない**。
   「馬固有の情報」を壊す操作なので、本物のシグナルもリークも同じように消える。
   🔑 **確実なのは「同じ特徴量を別実装で作って値を突合する」こと**。
   新特徴量は必ず**本番パイプラインで**測ること（検証用の使い捨てスクリプトの
   数字を採用根拠にしない）
   🔑 **逆に「固有情報が無い」を言うときは、残差ではなくアーム比較（入れる／抜く）で示す**。
   2026-09-16に `f_last1_rank` を「線形残差の単独AUC 0.5047 だから他2列の上に
   何も足していない」と断定したが、完全OOSで入れ／抜きを測ると **+0.0091**（3窓とも
   同符号）で**誤りだった**（2026-09-17に訂正）。残差の単独AUCは**直交化した成分の
   線形識別力**しか見ておらず、**木が使う交互作用の経路を塞げない**。
   ⚠ 「本番から抜いてよい」（B2−B1 +0.0002）と「固有情報が無い」は**別の主張**。
   前者しか測っていないのに後者を書かない
   🔑 **主張ごとに測定器を決め、それを仮説登録時に書く**（2026-09-17 に一般則化）。
   「独立情報が無い」→ X なし vs X あり ／「非線形性が重要」→ 線形X vs 非線形X ／
   「本番から削除できる」→ Production vs Production−X ／「市場を超える」→ Market vs Market+X。
   重要な**否定**結論は**データ経路が異なる2つ以上**の測定で示す
   （同じ計算列に統計を3つ当てても同じ嘘を3回見るだけ。PLθは3検査すべて通って漏れた）。
   ⚠ **結果を見てから測定器を足さない**
9. **的中率が上がることと回収率が上がることは別物。混同しない**。
   馬券は**最終オッズで払い戻される**ため、当たりやすい馬を選ぶ操作は同時に配当を縮める。
   2026-08-03に実測: 朝の1番人気(的中26.5%/回収76.5%)→直前の1番人気(的中**34.9%**/回収**84.7%**)。
   的中率が32%改善しても100%には届かない。オッズが最も買われた帯は勝率が7倍高いのに
   回収率58.2%で**無作為(80%)より悪い**。**「当たるようになった」は成果ではない。**
   新しい買い方を提案する前に、必ず**回収率で**評価すること。
   🔑 **`EV = AI確率 × オッズ` を買い目の根拠にしない**（2026-07-05・07-30・08-31 に3度否定）。
   AI確率は softmax T=3.5 で意図的に平坦にしてあり、オッズが上がっても
   6〜10%でほぼ横ばい。よって **EVはほぼオッズの単調増加関数**になり、
   「EVが高い馬」は実質「人気薄」を指す。本番8,546頭で EV>=1.0 は**回収57.9%**、
   買わない側(EV<1.0)が**75.0%**で、選別が完全に裏返る
10. **「本番の条件」を自分で決めつけない。ユーザーが実際にどう使っているかを確かめる**。
    2026-08-25、実オッズアンカー(D-2)を「本番＝朝の予想生成時点」として測り
    「+0.0043・基準未達」と報告した。直後にユーザーから「実際は締め切り直前まで待ち、
    直前オッズボタンを何度も押す」と指摘され、**答えていた問いが違った**と判明。
    同じ時点で測り直すと +0.0066（3窓とも同符号）で結論が変わった。
    🔑 数字は正しくても、**測っている条件が実際の使い方と違えば無意味**。
    North Star #8 は「値の作り方を疑え」だが、その手前に「**その条件で合っているか**」がある。
    🔑 差が複数の効果の和になっていないか毎回確認する。今回の +0.0254 は
    「順位→オッズ」と「朝→直前」が混ざった値で、**どちらの問いの答えでもなかった**
    （内訳は +0.0188 がユーザーの運用・+0.0066 が実装）
11. **対照群を置いたら、次に「本物があったらこの計測器は検出できるのか」を問う**。
    対照群は「偽の相関が出ないか」しか見てくれない。**本物でも必ず0になる設計か**は
    別に確かめる必要がある。2026-09-15、市場残差を「会場×馬場×距離」のセル平均で
    測ったが、1レースで3着内は必ず3頭なので**レース内の残差の和が構造的に≈0に固定**され
    （実測 std 16.4pt／独立なら155pt）、レース内で一定の属性でまとめると
    **市場が何をしていようが0に潰れる**設計だった。ラベルをシャッフルする対照群は
    ρ≈0 で「✅計測器は正常」と通っていた（偽セルも同じ理由で0になるため）。
    🔑 対策は **対照群B＝既知の効果を注入して検出できるか確かめる**こと。
    以後これを基準に必ず入れる（実例: `zansa/CRITERIA.md`）。
    🔑 **対照群の合格基準を書いたら、その閾値が統計量自身の SE より大きいかを先に確かめる**
    （2026-09-17 P3-01 で2件同時に踏んだ）。① 別経路への注入を「β_Z ≈ 注入量」で判定したが、
    「その変数の素の効果は0」という**測っていない仮定**を置いており、実際は −1.03pt あって
    正常でも必ず落ちた（正しくは**注入後 − 注入前 = 注入量**）。② シャッフル対照を
    「|β_shuffle| < |β|/3」で判定したが、閾値 0.37 が**推定量の SE 0.65 より小さく**、
    完全に正常な計測器でも半分以上落ちる。**SE より小さい閾値は「厳しい基準」ではなく
    「何も判定できない基準」**。1回の引きではなく**並べ替え分布**で見る。
   🔑 **以後の Phase 3 検証は、対照群を必ずこの2つの形で書く**（2026-09-17 にユーザーが
    全 Phase 3 へ適用すると決定）。
    **対照群A＝並べ替え分布**（レース内シャッフル 200 回。合格は「帰無が0中心」＝
    `|mean(β_shuffle)| < 2*std/sqrt(200)`。実測の β は並べ替え P で報告する。
    `|β_shuffle| < |β|/3` のような**1回の引きの大小比較は書かない**）。
    **対照群B＝注入の復元**（合格は `注入後 − 注入前 = 注入量`。
    `注入後 ≈ 注入量` と書くと「その変数の素の効果は0」という測っていない仮定が入る）。
    ⚠ SE の話が効くのは**統計量の閾値**。対照群B の許容差は**代数恒等式の検算**なので
    1e-3 のような厳しい値でよい（両者を混同しない）。
   🔑 同型の罠がもう1つある。**「差が大きいから本物」は言えない**。
    z2 ではセル間の傾き std 7.07pt に対し、値をシャッフルした偽データが 6.76pt で
    **観測/ノイズ = 1.05倍**だった。大きさを基準に置くなら、必ず**ノイズの大きさ**と
    並べて出すこと
12. 迷ったら**DESIGN.mdの「やってはいけないこと」表**を確認する。書いていなければ
    実装せずまず確認・相談する
