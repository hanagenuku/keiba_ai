```
📅 新潟 → pw01dde010420260206     ← 開催情報もURLも正常
```

1. 表示EVは Gumbelシミュレーション（**T=2.5で平坦化**）の確率を使っており、
   画面の勝率とも別物。平坦化は人気馬の確率を下げるのでEVが低く出る
2. そもそも `EV = 勝率 × オッズ` は買い目の根拠にならない（2026-07-05・07-30に否定済み）

**「EVが低いから悪い」は誤り**なので、単勝からEV表示を消した。

⚠ **短いオッズの軸を切る根拠は無い**。〜2.5倍の帯は76〜79%で、
むしろ中間帯（2.5〜3.5倍の72.6%、5〜8倍の34.5%）より良い。足切りは入れていない。

### 2026-08-08（📊EV買い目を「軸1頭ベース」に置き換え。的中率2.7%→改善）

#### なぜ変えたか：従来のEV方式は全ての軸で他に負けていた
ユーザーから「素人目にも当たりそうにない買い目を選んでいる」という指摘。
本番が実際に出した予想401レース × `race_dividends` の実配当で測った:

| 買い方 | 点数 | 的中率 | 回収率 |
|---|---|---|---|
| RL1-3 複勝（3点） | 1,203 | 43.9% | **80.1%** |
| RL1 複勝（1点） | 401 | **51.1%** | 79.4% |
| RL1 単勝（1点） | 401 | 24.2% | 77.1% |
| RL1 × RL2-3 ワイド | 776 | 19.3% | 70.6% |
| **★従来のEV方式（馬連）** | 1,166 | **2.7%** | 68.7% |

**的中率が最下位、かつ回収率でも上回っていない**（どの軸でも他に負けている
＝支配されている）。`stats.json` の実績でも馬連は44点で1点的中・回収0円。

⚠ **RL1単勝 24.2%/77.1% は、08-03に別データ2,000レースで測った
「朝の1番人気 26.5%/76.5%」とほぼ一致**しており、測定手法の妥当性が取れている。

#### 採用した構成（ユーザー提案）
```
① 単勝    軸(RL1)                         1点
② ワイド  軸 × 中穴（3着内確率順）           最大3点
③ 馬連    軸 × 中穴          合成オッズ >= 3.0 を保つ範囲で可変
④ 三連複  A - 中穴2頭 - (RL2..9 ＋ 中穴)    最大24点
```
中穴 = 単勝 **7〜30倍** のうち `cal_prob`（3着内確率）が高い順。
合成オッズ = `1 / Σ(1/各オッズ)`。取りガミ防止のための足切り。

#### 🔴 三連複の2列目に上位人気を置くと崩れる（実測）
ユーザー提案の `A-BC-BCDEFGHIJ`（15点）の `BC` を2通り解釈して測った:

| 三連複の組み方 | 的中率 | 回収率 | 高配当1本抜き |
|---|---|---|---|
| A - **RL2,RL3** - RL2..10 | 1.78% | **56.3%** | 52.2% |
| A - RL2,RL3 - RL2..7＋中穴2 | 2.46% | 58.3% | 53.4% |
| **A - 中穴2 - RL2..6＋中穴** | 2.37% | **157.8%** | **107.0%** |
| A - 中穴2 - RL2..9＋中穴 | 1.63% | 121.2% | 93.4% |
| （比較）軸流し 相手RL2-7 | 1.90% | 103.7% | 80.6% |

**2列目は中穴でなければならない。** 11通り試した中で、この向きだけが一貫していた。

3列目は **RL2..9（広い版）を採用**。見出しの回収率は狭い版(RL2..6)が高いが、
**より深い頑健性検査では広い版が上**（3本抜き 61.9% vs 54.9%、
プラスの日 5/12 vs 4/12）。見出しの数字は高配当1本依存で信用できない。

#### ⚠ 回収率は控除率を超えていない（採用の根拠にしていない）
100%超はすべて頑健性検査で落ちた:
```
A - 中穴2 - RL2..6＋中穴 : 157.8%
  高配当2本を抜くと      : 61.6%
  前半 266.9% → 後半     : 49.3%
  プラスだった開催日      : 4/12日   日別中央値 63.7%
  95%信頼区間(日ブロック) : [56.7%, 307.3%]
```
2026-07-27の買い目フィルタ（76点で182.8% → 2,000レースで71.3%）と同じ壊れ方。
⚠ **11通り試して最良を報告している**ことも明示すべき多重比較の問題。

**この構成を採用した理由は「儲かるから」ではなく「従来方式より的中率が
6倍良く、買う理由が見えるから」**。アプリには
**「🧪 検証中 — 的中率は改善しましたが、回収率はまだ控除率を超えていません」**
と常時表示する。

### 2026-08-07⑤（アプリが「取得できません」と誤報する不具合を修正。実際は成功していた）

#### 症状（ユーザー報告・先週も発生）
ボタンを押して35分待つと「取得できませんでした」と出るのに、
**手動でアプリを更新すると実は正常に取得できていた**。

#### 原因は3つ重なっていた（`index.html` の `_startPolling`）
1. 🔴 **時間切れ時に一度も確認せず諦めていた**。スマホがバックグラウンドで
   タイマーを止めるため、画面を消していると復帰時の**最初のティックが
   いきなり35分超**になる。そのまま `alert` に直行していた
2. 🔴 **確認スケジュールが `elapsed % 30 < 2` という剰余判定**だった。
   タイマーが間引かれて `elapsed` が飛ぶと判定窓を丸ごと跨ぎ、
   一度も確認されない
3. **アプリに戻ってきた時に確認する仕組みが無かった**

#### 実測（`tests/test_polling.mjs` を旧コードに当てた結果）
復帰時刻を1秒ずつずらして30通り試すと、
**30通り中28通りで「成功しているのに取得できません」**と表示された
（`elapsed` がたまたま30の倍数の時だけ当たる）。
本当に失敗したケースもタイムアウト扱いになっていた。修正後は 0/30。

#### 修正
- 確認の間隔を**剰余ではなく「前回確認からの経過時刻」**で判定
- **諦める前に必ずもう一度確認する**
- `visibilitychange` / `focus` / `online` で**復帰した瞬間に即確認**
- 判定順を **①データが実際に更新されたか → ②status=success → ③status=failure** に変更
  （同じボタンで2本走って片方だけ失敗する場合があり、statusだけ見ると
  成功したのにエラー表示になる。実際に本日2本同時起動が発生している）
- `_restorePolling` も、時間切れでも**捨てる前に結果を確認**するよう変更
- ボタンを押していなくても、**アプリに戻った時に `generated_at` が
  変わっていれば自動で読み直す**（土日朝8時の自動refresh対策。
  60秒以上離れていた時のみ・変化が無ければ何もしない）

#### テスト

### 2026-08-07④（🔴金曜予想が本番で停止。`agari_rank=None` で `calc_all()` が TypeError）

#### 何が起きたか
金曜予想ボタンで **35レース・443頭のオッズまで正常に取得できていたのに**、
`calc_all()` の途中で落ちて**その回の予想が丸ごと失われた**（2回連続失敗）。

```
File "src/features/engine.py", line 753, in calc_race_content_score
    agari_pct = (finishers - agari_rank) / max(finishers - 1, 1)
TypeError: unsupported operand type(s) for -: 'int' and 'NoneType'
```

#### 🔴 原因：`.get(key, default)` は「キーはあるが値が None」を救えない
2026-08-03② で `agari_rank` の欠落バグを直した際、**「未記録なら None を明示する」**
設計にした（学習側 `_get_history_before` / 推論側 `get_history_from_db` の両方）。
ところが消費側は前から `r.get('agari_rank', finishers)` と書かれており、
**`.get()` の既定値はキーが存在しない時にしか効かない**。
キーが存在して値が None、という**新しい状態**が素通りして算術に流れた。

⚠ **これは「片方だけ直して消費側が追従していない」型の事故**で、
2026-08-03④の `corner_3`（スキーマ文書は正しかったが読む側が移行に追従していない）と
同じ構造。**「欠損の表し方を変えたら、その値を読む全箇所を洗う」**必要がある。

⚠ **モデル再学習（③）は無関係**。同じコミット上で動いたので疑ったが、
落ちたのはルールベース側の `f_recent`→`calc_race_content_score` で、
XGB推論には到達すらしていない。**08-03②以降これが初めての `calc_all()` 実行だった**
（08-01/02の週末は修正前、以降レース開催なし）ため、4日間潜伏していた。

#### 修正
`_hist_num(value, default)` を新設し、**None を既定値に落とす**（`.get()` と違い
値が None でも効く）。適用箇所:

| 関数 | フィールド |
|---|---|
| `calc_race_content_score` | place / finishers / margin / agari_rank |
| `f_rl` | finishers / agari_rank |
| `f_maturity` | place |
| `calc_features_for_xgb` | place（6箇所の `<= 3` 比較・`places` リスト） |

`agari_rank` は **None・センチネル99・頭数超過**をすべて「不明＝最下位相当」に寄せる
（`horse_type._valid_rank` と同じ考え方。2026-08-06に同型バグを別途修正済み）。
`place` は推論側SQLで **COALESCE されておらず None になりうる**ことも確認した。

#### テスト
`tests/test_history_none_fields.py` 新規6テスト。North Star #6 に従い
**本番と同じ経路**（`save_history_db()` で書き込み→`get_history_from_db()` で読み出し）
のレコードで検証。**修正前は6件すべて本番と同じ TypeError で失敗**することを確認済み。
「不明が最下位相当になる」という方向性も固定した（None が最速扱いになると
データの無い馬ほど高評価という逆転が起きるため）。
