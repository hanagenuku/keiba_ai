# Phase 4 設計：AI分析を「予想＋印＋買い目」に変換して販売する

> 🔴 **この文書は商品研究（`biz/`）に属する。** AI研究（AUC・回収率）と同じ文書で論じない。
> 🔴 **予想ロジックは変更しない。** Phase 3 までのAIをそのまま使い、出力を読んで整形するだけ。

## 0. 実装する前に確定させた3つの矛盾（重要）

ユーザーが示した商品フォーマット（§2・§25 の実例）には、**このシステムが持っていない情報**が
含まれていた。そのまま実装すると §12「存在しない陣営コメントを作らない」に自分で違反する
コードを作ることになるので、先に切り分けた。

### ① 陣営コメント・調教は書けない（データが存在しない）

示された実例の以下の文は、**こちらの情報源には存在しない**。

| 実例の文 | 状態 |
|---|---|
| 「陣営によればこの距離は少し忙しいとのこと」 | 🔴 **陣営コメントは取得経路が無い**。JRA公式に無く（2026-08-16 に4回検証して打ち切り）、netkeiba の該当欄は有料 |
| 「この中間も引き続き好調をキープしているとのこと」 | 🔴 同上 |
| 調教タイム | 🔴 JRA公式に機械可読な値が存在しない。jugem は 1頭/開催日で 2026-09-25 に閉じた |
| パドックの気配 | 🟡 ユーザーの手入力が 987行あるが**予想に繋いでいない**（効果は一度も測っていない） |

→ **見解は「こちらが実際に持っている事実」だけで書く。** 持っていない項目は
**書かない**（推測で埋めない）。文章が短くなることを受け入れる。
Web で取得した情報を使う場合のみ「○○によると」と出典を付ける（§12 のルールどおり）。

### ② 地方競馬（船橋・川崎など）は対象外

実例は **船橋9R**（地方競馬・NAR）だが、このシステムは **JRA専用**。
`history.db` も JRA のみ、スクレイパーも JRA の JRADB のみ。
→ **商品の対象は JRA のみ**。実例は他の予想家のフォーマットを借りたものとして扱い、
形式だけを採用する。

### ③ §6 パターンC（穴候補）は測定で逆が出ている

§6 のパターンのうち1つは、**このプロジェクトが3回測って否定した方向**そのもの。

| §6 のパターン | 測定結果 |
|---|---|
| **パターンC** 能力5位 × 適性1位 × **市場低評価 → 穴候補** | 🔴 **逆**。`EV = AI確率×オッズ` で選ぶと回収 **57.9%**（買わない側75.0%）／AIが市場より強気+3以上は複勝率 **12.7%**・回収 **53.0%**／`corr(gap, 符号つき誤差) = −0.1213`＝**市場と食い違うほどその方向にAIが間違っている**（2026-07-30 / 08-03 / 08-31 の3回） |
| パターンD 能力1位×適性1位×市場1番人気 → オッズ次第で見送り | ✅ 方向は測定と整合（1番人気の複勝回収85.6%は最良だが100%未満） |

→ **「AIが市場より高く見ている馬を穴として推す」形は商品に入れない。**
代わりに**逆向き**（市場が高く見ている馬をAIが低く見ている＝疑う側）を使う。
こちらは測定で機能している（市場1番人気のうち素のAIが6位以下 → 複勝率 **68.5%→51.4%**）。

🔑 **つまり印は「買う方向」に使い、乖離は「疑う方向」にだけ使う。**
これは §10「買わない」も予想として販売する、と同じ方向を向いている。

## 1. 印の決め方（固定ルール・後から変えない）

```
◎ = rl_rank 1     （＝アプリの軸。conf が測られている対象そのもの）
○ = rl_rank 2
▲ = rl_rank 3
△ = rl_rank 4, 5
```

**◎を rl_rank1 から動かさない理由**：唯一「市場を上回っている」と測れているのは
`conf`（軸の3着内確率。当てやすさ AUC **0.6041** vs 市場 0.5708・3,560レース）で、
これは **rl_rank1 を軸としたときの値**。◎を別の馬に動かすと、
商品に載せる信頼度の根拠が消える。

⚠ §4「AI順位1位→◎と文章化するだけでは普通のAI予想と差がない」という指摘は正しい。
差が出るのは**印の付け方ではなく、なぜその順位なのかの説明と、疑う側の指摘**のほう。
印そのものは素直に固定し、説明で差を付ける。

|---|---:|---|

### 固め／中穴の分け方

```

中穴 = 単勝 7.0 〜 30.0 倍
大穴 = 30.0 倍超 → 相手に入れない
```

🔴 **境界は商品側で発明していない。** `src/betting/axis_bets.py` の
`ANA_ODDS_MIN` / `ANA_ODDS_MAX`（2026-08-08 に実測でオッズ帯を比べて決めた値）を
そのまま import している。実測（ワイド1点の回収率／高配当1本抜き）:

⚠ 102.5% は1本抜きで87.4%まで落ちる。**記事には1本抜き後の数字しか書かない**
（100%超の生の数字を有料記事の見出しに置くと、自ら禁じた誇大表示になる・§20）。

🔑 **「バランスよく」の実体は中穴枠を別に確保すること。** 相手を rl_rank の上位から
順に取るだけだと、AI+市場の順位は市場に引っ張られるので**上位が固めで埋まって
中穴が1頭も入らない**。固め枠・中穴枠を分けて取る。
⚠ その内訳（固め3＋中穴2）は**こちらが決めた比率で実測の裏付けは無い**。

## 4. 資金配分（比率で示す・金額は換算例）

```
strong : 複勝 25% / 三連複 20% / ワイド 15% / 馬連 15% / 三連単 15% / 単勝 10%
light  : 複勝 40% / ワイド 20% / 馬連 15% / 三連複 15% / 単勝 10%
```
⚠ **傾斜配分で期待値は動かない**（2026-08-18③：総期待値＝各EVの加重平均。
全EV<1ならどう配分しても<1）。配分を示すのは**分散を抑えるため**であって、
「配分で勝てる」とは書かない。
⚠ 連系を厚くしていないのは、控除率が高い側へ資金を寄せる根拠が無いため。
読者が連系を厚くしたいなら各自調整してよい（そう書いてある）。

🔴 **100円単位への丸めは最大剰余法**。各券種を独立に四捨五入していたとき、
1,000円・6券種で**複勝100円 < ワイド200円**になった（比率は 0.25 vs 0.15）。
券種が増えると比率の大小が金額で逆転するので、合計を固定して剰余の大きい順に配る。

🟢 **2026-10-26: 配分は「コースの中」だけで出す。**
上の比率はそのまま使うが、**コースに含まれる券種だけを取り出して正規化する**
（堅実コース = 単勝・複勝 ／ 勝負コース = 馬連・ワイド・三連複・三連単）。
全券種にまたがる比率は作らない（`allocation_ratio` は空になる。キーは
アーカイブの互換のため残してある）。⚠ `ALLOC_STRONG` / `ALLOC_LIGHT` /
`AMOUNT_EXAMPLES` の**値は1つも動かしていない**。
⚠ 比率の表示は `int(v*100)` だと 0.29 が 28% になる（0.29×100 = 28.999…）ので
四捨五入で出す。並びは比率の大きい順（換算例と同じ順序）。

🟢 **2026-09-29 に文面を §10 に合わせた**（戦略文書 §10「資金配分は、オッズと資金に
応じて各自調整 とする」）。比率は「目安」・金額は「換算例（推奨額ではありません）」と明記し、
`tickets.ALLOCATION_NOTE` を記事とアーカイブの両方に載せる。
**券種が1つのレースでは比率表も換算例も出さない**（自明な表は載せない）。
`AMOUNT_EXAMPLES`（1,000 / 3,000 / 5,000円）の値は変えていない。

### 🟢 2026-10-26②: 「最適な配分にしてほしい」への回答（算数で決まる2点だけ直した）

ユーザー指示「掛け金を最適な配分にしてください」。

🔴 **回収率を上げる「最適配分」は存在しない。** 総期待値は各買い目の期待値の
加重平均なので、全部の期待値が1未満ならどう振り分けても1未満。Kelly も
`f* = (p·o − 1)/(o − 1)` が負＝「賭けるな」を返す。2026-08-18③（43セル）と
2026-08-20（541レース・傾斜を総当たりして行き先は3本抜きで 66%→74% ＝
**損が減るだけ**）で測って閉じており、CLAUDE.md の「もう提案しなくていいこと」に
入っている。**この方向に戻らない。**

そのうえで実データ（2026-10-25 の27レース）を当てたら、**算数の defect が2つ**あった。
どちらも測定ではなく算数なので、新しい検証なしで直せる。

| | 何が壊れていたか | 直し方 |
|---|---|---|
| **(A) 当たったのに損をする** | ◎が2〜3着＝複勝だけ的中のとき **元本割れ 12/27レース。strong は 9/9 すべて**（最悪 0.781 ＝ **−21.9%**）。機序は 複勝1.1倍 に対し単勝へ29%回すと 0.71×1.1 = 0.781 になるだけ | 単勝に回す比率の上限を **`1 − 1/複勝オッズ`** にする（複勝1.1倍→最大9% / 1.4倍→28% / 2.9倍→65%）。**金額（100円単位）で決める**——比率を丸めてから `allocate` に渡すと各券種に最低1単位が置かれ、1,000円・複勝1.1倍で複勝900/単勝100＝990円 と取りガミが復活する |
| **(B) 換算例が買えない額だった** | 1,000/3,000/5,000円 を全コースに当てていたが、37点の勝負コースは1点100円でも 3,700円。券種ごとの金額を点数で割ると**三連単 900円 ÷ 17点 = 53円/点** で100円単位にならない | ① 換算例の先頭を**そのコースの最低額（点数×100円）**にする ② 多点のコースは金額ではなく**1点あたりの単価（100/200/300円）**で示す |

実測: **81/81 の換算例で「複勝だけ当たって元本割れ」が消えた**（直す前は 12/27 が元本割れ）。

⚠ **上限としてしか使わない（上へ引き上げない）。** 堅実コースは「固く当てにいきたい
人向け」なので、複勝が高いからといって単勝へ寄せるのは趣旨に反する。
`ALLOC_STRONG` / `ALLOC_LIGHT` / `AMOUNT_EXAMPLES` の**値は1つも動かしていない**
——従来の比率が上限側の基準として残り、オッズが低いときだけ下へ動く。
⚠ 複勝オッズは発売中は**幅**で出るが、`latest.json` に入るのはその中央値。
どの馬が3着内に入るかで下限寄りになりうるので、保証は「記事作成時点の表示値での」話。
記事に明記する。
⚠ 連系（勝負コース）に同じ計算は当てない。組み合わせ券種の配当は**推定値**しか無く、
推定で配分を決めると推定が甘い券種ほど厚くなる（2026-08-08 に決済で同じ罠を踏んでいる）。
よって勝負コースは**1点の単価をそろえる**だけで、券種間に厚薄を付けない。
`allocation_ratio` はその結果（点数比例）を出す。

🟡 **直していない非整合を1つ記録する（判断が要るため勝手に変えない）。**
`ALLOC_*` では 勝負コースの **ワイドと三連複の厚さの順序が勝負度で入れ替わる**
（strong: 三連複 0.20 > ワイド 0.15 ／ light: ワイド 0.20 > 三連複 0.15）。
根拠は文書に無い。旧来の1ブロック表示では薄まっていたが、コース分割で表に出た。
どちらが正しいかは測っていないので、こちらでは決めない。
🔑 ただし勝負コースを**単価そろえ**にしたので、**この順序は記事に出なくなった**
（出るのは点数比例の比率）。`ALLOC_*` の値はそのまま残してある。

## 5. 見解に書いてよい事実（history.db から機械抽出）

| 脚質 | `running_style` |

|---|---|

🔴 **リーク防止**：見解に使う履歴は **対象レースの日付より前** のものだけに厳格に絞る。
`history.db` には対象レース自身の結果が入ることがある（結果取得後に生成し直した場合）。

⚠ **新馬戦は書ける事実がほぼ無い**（全馬に過去走が無い）。
2歳未勝利でも1〜2走。conf が高く出るのは未勝利・新馬に偏るので
（2026-08-24 E-1：未勝利・新馬 82.7% vs それ以外 79.2%）、
**「conf が高い＝書ける事実が多い」ではない**。商品化するときに効いてくる制約。

## 6. 予想を後から変更しない仕組み（§18）

```
prediction_archive/YYYY-MM-DD/{race_id}.json
```
- `latest.json` は当日 refresh で**上書きされる**（2026-09-19/22 に実害が出ている）ため、
  公開時点のファイルが別に永続しないと「後から変更していない」ことを示せない
- **同じ race_id が既に保存されていれば上書きしない**（`overwrite=False` が既定）。
  コードで固定し、テストで守る
- 保存するもの：公開時刻・AI順位・AI単独順位・適性順位・市場順位・オッズ・印・
  見解・買い目・推奨配分・レース信頼度・**生成に使った入力のハッシュ**

| 要素 | 測定状態 |
